# Часть I. Как устроен тенант

## 1. Термин: тенант — это `Organization`, а не `Company`

Это первое, что путают, и путаница дорогая:

| Сущность | Что это | Скоуп |
|----------|---------|-------|
| **`Organization`** | **тенант**: компания-заказчик, которая купила Sellevate | `organization_id`, клейм `org_id`, заголовок `X-Organization-Id` |
| `Company` | CRM-запись продавца: компания, которой он звонит | `WHERE UserId = ...`, внутри организации |

Реестр организаций живёт в отдельном сервисе **`organization-service`** (порт 5010, БД `organization`).
Остальные сервисы держат у себя голый `uuid organization_id` **без внешнего ключа** и узнают о
жизненном цикле организации из Kafka — тот же паттерн, что уже был для пользователей.

## 2. Что тенант-скоупится, а что нет

Три категории таблиц, и от категории зависит и колонка, и политика RLS, и EF-фильтр:

| Категория | Колонка | Примеры | EF-фильтр |
|-----------|---------|---------|-----------|
| **Данные тенанта** | `organization_id NOT NULL` | прогресс, попытки, диалоговые сессии, задания, компании CRM, уведомления | `x.OrganizationId == current` |
| **Библиотека контента** | `organization_id NULL` = глобальный, не-null = копия организации | `Skills`, `Topics`, `Lessons`, `Exercises`, `Techniques`, `ReferenceMaterials`, `DialogBundles`, `DialogModes` | `x.OrganizationId == null \|\| x.OrganizationId == current` |
| **Платформенное** | колонки нет | `default_avatars`, `exercise_type_prompts`, служебные таблицы outbox | — |

Нуллабельная колонка у контента — это то, что позволяет одному базовому курсу обслуживать всех
заказчиков без форка. См. §12.

## 3. Путь запроса — три слоя изоляции

```
браузер
  │  Authorization: Bearer <JWT>            ← клеймы: sub, role, org_id, org_role
  ▼
GATEWAY (YARP)
  │  1. валидирует JWT ровно один раз
  │  2. ВЫРЕЗАЕТ любые клиентские X-User-Id / X-Organization-Id
  │  3. ставит их заново из проверенного токена
  ▼
СЕРВИС
  │  TenantContextMiddleware читает X-Organization-Id → ITenantContext (scoped)
  │  нет заголовка на [TenantScoped]-маршруте → 403 ещё до контроллера
  ▼
EF Core                     ← СЛОЙ 2: global query filter (удобство, НЕ безопасность)
  │  снимается IgnoreQueryFilters(), не действует на ExecuteUpdate/Delete и raw SQL
  │  TenantSaveChangesInterceptor на записи: чужой organization_id → исключение
  ▼
POSTGRES                    ← СЛОЙ 3: RLS (единственная настоящая граница)
     политика USING + WITH CHECK по current_setting('app.organization_id')
```

**Правило, из которого нет исключений, кроме двух названных:** организация **никогда** не приходит
из body, query или route. `?organizationId=...` игнорируется, а не валидируется. Механически это
держит `scripts/tenancy-boundary-lint.py` в CI.

Два легальных исключения — оба у платформенного суперадмина, оба минтят новый токен, а не
параметризуют обычный маршрут:
`POST /admin/platform/impersonation` и `POST /admin/platform/organizations/bootstrap-admin`.

## 4. Слой 3 подробно: как устроена RLS

```sql
ALTER TABLE <table> ENABLE  ROW LEVEL SECURITY;
ALTER TABLE <table> FORCE   ROW LEVEL SECURITY;

CREATE POLICY <table>_tenant_isolation ON <table>
  USING      (<platform-mode OR> organization_id = NULLIF(current_setting('app.organization_id', true), '')::uuid)
  WITH CHECK (organization_id = NULLIF(current_setting('app.organization_id', true), '')::uuid);
```

Четыре детали, каждая из которых решает, работает это или является театром:

1. **`FORCE` обязателен.** Без него владелец таблицы обходит собственную политику — а миграции
   ходят как раз под владельцем.
2. **`WITH CHECK` обязателен отдельно.** `USING` фильтрует только чтение; запись чужого
   `organization_id` блокирует именно `WITH CHECK`. В `WITH CHECK` платформенного режима **нет**:
   сотрудник платформы может читать поперёк организаций, писать — нет.
3. **`NULLIF(..., '')`, а не просто `missing_ok`.** Пул соединений возвращает пустую строку, а не
   `NULL`, после первого использования. Поймано интеграционным тестом на живом Postgres.
4. **`SET LOCAL`, не `SET`.** Транзакционная область. Обычный `SET` протекает на следующий запрос,
   который возьмёт то же соединение из пула. Поэтому же на тенант-скоупных контекстах **запрещён**
   `AddDbContextPool` — за этим следит `scripts/tenancy-pool-lint.py`.

Выставляет GUC один общий `TenantConnectionInterceptor` в `BuildingBlocks`, а не семь копий по сервисам.

**Почему RLS сейчас не фильтрует ничего:** все compose-файлы подключают сервисы под
`${POSTGRES_USER}` — владельцем схемы и суперпользователем. `FORCE` к суперпользователю не
применяется. Включение = переезд на роль `sellevate_app` (Часть II, шаг 12).

## 5. Запись: `TenantSaveChangesInterceptor`

- на `Added` — проставляет `OrganizationId` из контекста;
- на `Modified` / `Deleted` — сверяет с `OriginalValues` и **запрещает менять колонку после создания**;
- чужая организация → `CrossTenantWriteException` (без утечки чужого id в текст ошибки);
- перекрыты **обе** перегрузки, `SavingChanges` и `SavingChangesAsync` — sync-only интерцептор в
  этой кодовой базе не сработал бы никогда, весь код async;
- `IsSystem`-режим проверку обходит намеренно (см. §8).

## 6. Роли: платформенные и организационные — это два разных словаря

| Клейм | Значения | Кто это |
|-------|----------|---------|
| `role` (платформенный) | `User`, `Admin`, `SuperAdmin` | сотрудники Sellevate; `Admin`/`SuperAdmin` = «платформенный персонал», видят поперёк организаций |
| `org_role` (организационный) | `Manager`, `TenancyAdmin`, `TenancySuperAdmin` | люди внутри организации заказчика |

Разделение введено 2026-08-16. Устаревшее имя `OrgAdmin` **отвергается**, не маппится.

| Может | Manager | TenancyAdmin | TenancySuperAdmin | Platform Admin | Platform SuperAdmin |
|-------|:---:|:---:|:---:|:---:|:---:|
| Учиться, проходить задания | ✅ | ✅ | ✅ | — | — |
| Видеть дашборд команды, выдавать задания | — | ✅ | ✅ | — | — |
| Править профиль организации, override'ы контента | — | ✅ | ✅ | — | — |
| Приглашать/отключать людей (`/invites`, `/memberships`) | — | — | ✅ | — | ✅ |
| CRUD организаций, имперсонация, bootstrap первого админа | — | — | — | — | ✅ |
| Читать поперёк организаций (платформенный режим) | — | — | — | ✅ | ✅ |

## 7. Доступ: публичной регистрации нет

Вход закрытый, и маршрута, который мог бы стать публичной регистрацией, в бэкенде нет.

1. **Организацию создаёт платформенный суперадмин** — `POST /organizations`.
2. **Первого админа организации** — `POST /admin/platform/organizations/bootstrap-admin`
   `{organizationId, email}`. Роль всегда `TenancySuperAdmin` и из запроса **не берётся**. `409`,
   если у организации уже есть активный суперадмин или ждущий инвайт — то есть чёрным ходом в
   работающего заказчика это не станет.
3. **Дальше приглашает сам заказчик** — `POST /invites` `{email | emails[], role}`. Массовый запрос
   частично успешен: плохие адреса уезжают в `rejected` с причиной. Токен инвайта отдаётся один раз,
   в БД лежит только SHA-256, письмо шлёт MailerSend.
4. **Принятие** — `POST /auth/invites/{token}/accept` (публичный, не тенант-скоупный: организация
   восстанавливается из HMAC-подписи самого токена). Если аккаунт с таким адресом уже есть — ему
   добавляется членство, второй пользователь не создаётся.
5. **Вход трёхшаговый:** `POST /auth/login/start {email}` → `{method: password|oidc|saml}` → дальше по
   способу. Способ входа — настройка организации (`organization_auth_config`). Это шов под SSO;
   сам SSO не реализован (40.36 `[SKIP]`).
6. **Suspend организации** гасит вход: `/auth/login`, `/auth/google`, `/auth/refresh` и приём инвайта
   отвечают `403 "Organization suspended"`.
7. **Отключение сотрудника** (`DELETE /memberships/{userId}`) — это `status = deactivated`, а не
   удаление: история менеджера принадлежит организации. Маршрута, удаляющего членство, нет.

**Имперсонация** (`POST /admin/platform/impersonation`) выдаёт намеренно **более слабый** токен, чем
тот, который её запросил: `role = User` (не `SuperAdmin` — поэтому второй имперсонации не будет),
`org_role = TenancyAdmin` (на ранг ниже — заимствованную организацию нельзя переукомплектовать),
жизнь 15 минут, refresh-токена нет, аудит-строка коммитится **до** выдачи токена.

## 8. Три режима тенант-контекста

У запроса есть заголовок. У фоновой задачи — нет. Поэтому каждая фоновая работа обязана **объявить**
свой режим, и все они перечислены в [`BACKGROUND_JOBS.md`](BACKGROUND_JOBS.md):

| Режим | Кто так работает | Что делает |
|-------|------------------|------------|
| **Тенант из конверта** | Kafka-консьюмеры | берут `organizationId` из `EventEnvelope` и **падают**, если его нет |
| **Перечисление по организациям** | свипы (автоповторы, дедлайны, адаптация контента) | цикл: организация → `SetOrganization` → работа в её скоупе |
| **Системный** | outbox-релей, бэкфилл версий, чистки платформенных таблиц | `EnterSystemMode`, проверки записи обходятся осознанно |

**Семь** из них помечены `Needs BYPASSRLS = Yes`. Это ровно те семь мест, где в продакшн-коде стоит
`IgnoreQueryFilters()`. В день переезда на роль `sellevate_app` они **замолчат без ошибки** —
см. Часть II, шаг 12.

## 9. События, outbox, Kafka

- `EventEnvelope` несёт `OrganizationId` — ломающее изменение общего контракта, сделанное один раз,
  до появления первого тенант-скоупного консьюмера.
- `OutboxMessage` получил колонку `OrganizationId`; `PartitionKey` остался user id (переезд на
  `org:user` перетасовал бы партиции без выигрыша).
- Базовый консьюмер выставляет тенант-контекст из конверта **до** обработки и падает без него.
  Молча обработать событие без организации нельзя.
- Топики создавать руками не надо — `KafkaTopicProvisioner` делает это сам.

## 10. Mongo и Redis

- **Mongo** (диалоговые сессии в ai, история чатов в social): поле `organizationId` в документе +
  составные индексы. Оба бэкфилла — `mongo/40.11_dialog_sessions_organization_backfill.js` и
  `mongo/40.13_chat_conversations_organization_backfill.js`.
- **Redis**: организация входит в **ключ**, а не в значение. Старые ключи без организации истекают
  сами по TTL — кроме одного: `presence:online` TTL не имеет и уйти сам не может.

## 11. Индексы и уникальность

Композитные индексы строятся с `OrganizationId` **первой** колонкой. Важное следствие для уникальности:
до перестройки индексов в `Skills` / `Topics` / `Techniques` остаются старые **глобально-уникальные**
индексы по слагу — то есть **второй заказчик со своим `objections` просто не заведётся**.
Перестройка идёт через `CREATE INDEX CONCURRENTLY` и намеренно **не** входит ни в одну EF-миграцию и
ни в один `DatabaseBootstrapper`: это стопорило бы readiness и гонялось бы с репликами.

## 12. Контент: почему курс не форкается на заказчика

- **40.15 — иммутабельные версии уроков.** `Lessons` + `LessonVersions`, канонический `content_hash`,
  ровно один черновик, заморозка при публикации.
- **40.16 — прогресс привязан к версии урока**, а не к уроку. До этого правка урока задним числом
  переписывала историю прохождений и искажала метрики.
- **40.17 — версионирование программы и зачислений:** зачисленный учится по версии, на которой
  зачислен, пока его не перевели.
- **40.18 — override'ы copy-on-write:** организация правит урок → получает свою копию, глобальный
  оригинал не трогается. **Автослияния нет намеренно** — расхождение попадает в очередь `stale` на
  ревью человеком.
- **40.19 — профиль организации и параметризация:** плейсхолдеры `{{organization.*}}` подставляются из
  профиля, `banned_claims` уходит и в промпт персоны, и в промпт оценщика. Это убирает большинство
  поводов форкать урок вообще.

⚠️ В базовых уроках **пока не расставлено ни одного `{{organization.*}}`** — это контентная работа,
её никто не делал. Правила: `../CONTENT_PARAMETERIZATION.md` §6.

## 13. Задания и ИИ-квоты — коротко

- **Задание считается сделанным по порогу качества, а не по факту прохождения** (`dialog_score`,
  `exercise_accuracy`). `failed_threshold` — видимое состояние, а не тишина.
- Аудитория задания — **правило**, а не список; разрешается запросом к identity-service в момент
  выдачи. Контент — ссылки на **замороженные версии**, поэтому все одиннадцать типов упражнений
  рендерят задание без нового кода.
- Автоповторы: укороченная перевыдача на +7 и +21 день, идемпотентность — существование строки.
- **Квоты считаются в токенах, деньги только показываются.** Правка `AiQuotas:PricePerMillionTokens`
  перерисовывает историю и **не двигает ни один лимит**. Непрайсованная модель приходит с
  `estimatedCost: null` и флагом — никогда не нулём.
- Деградация упорядочена: интерактивная работа идёт до 100% лимита, фоновая останавливается на
  `100% − BatchReservePercent` (по умолчанию 90%). Класс объявляет вызывающий заголовком
  `X-Ai-Workload`; **отсутствие заголовка = интерактивный**.

## 14. Организация по умолчанию

Существующая инсталляция, жившая до тенантности, целиком садится в одну организацию с фиксированным
UUID **`00000000-0000-4000-8000-000000000001`** (slug `default`, имя `Sellevate`). Он константный, а не
случайный, потому что пишется в две базы без внешнего ключа между ними — и повторный прогон, откат и
вопрос в поддержку должны указывать на одно и то же. **Этот id обязан совпадать во всех шагах
раскатки** (`ORGANIZATION_ID` у всех пяти скриптов).

# Часть II. Раскатка на сервере — по шагам

> Прод: один сервер (Amsterdam, Timeweb, Ubuntu 24.04), всё через Docker Compose за Traefik.
> Все команды выполняются **на сервере, из корня репозитория**.
>
> Ниже используется сокращение:
> ```bash
> cd /path/to/Repository
> export DC="docker compose -f docker-compose.yml -f docker-compose.prod.yml"
> ```
>
> **Считать это окном обслуживания.** Шаги 4–9 включают промежутки, в которых пользователи видят
> пустой прогресс. Фронтенд лучше погасить на всё окно.

## Шаг 1 — бэкап (не пропускать)

Семь баз Postgres (`notification` и `analytics` баз не имеют — они Redis/без хранилища) + Mongo:

```bash
mkdir -p ~/backups/$(date +%F) && cd ~/backups/$(date +%F)
source /path/to/Repository/.env
for db in identity learning ai company gamification social organization; do
  docker compose -f /path/to/Repository/docker-compose.yml exec -T postgres \
    pg_dump -U "$POSTGRES_USER" -Fc "$db" > "$db.dump"
done
docker compose -f /path/to/Repository/docker-compose.yml exec -T mongo \
  mongodump --archive --db sallevate > mongo-sallevate.archive
```

Проверить, что дампы непустые (`ls -lh`), прежде чем идти дальше.

## Шаг 2 — проверить права роли, под которой пойдут миграции

**Без этого шага любая миграция «успешно» ничего не сделает.** Каждая миграция начиная с 40.9
включает `FORCE ROW LEVEL SECURITY`. Если роль миграций не суперпользователь и не имеет `BYPASSRLS`,
RLS начнёт фильтровать сами миграции.

```bash
$DC exec -T postgres psql -U "$POSTGRES_USER" -d postgres -c \
  "SELECT rolname, rolsuper, rolbypassrls FROM pg_roles WHERE rolname = current_user;"
```

Ожидается `rolsuper = t` **или** `rolbypassrls = t`. Если нет:

```sql
ALTER ROLE <migration_role> WITH BYPASSRLS;
```

## Шаг 3 — `.env` и переменные окружения

Новые переменные, появившиеся в фазе:

> ⚠️ **Связка `ASPNETCORE_ENVIRONMENT` ↔ `INTERNAL_SERVICE_SECRET` — прочитать обязательно.**
> Сегодня `docker-compose.yml` ставит `ASPNETCORE_ENVIRONMENT=Development` **всем десяти** сервисам,
> а `docker-compose.prod.yml` — оверлей только для Traefik и переменную не меняет. Отсюда два факта:
> 1. `POST /demo/token` **выдаёт настоящий JWT, подписанный продовым ключом, и доступен из интернета**
>    (маршрут прячет себя только в `Production`). На изоляцию тенантов это не влияет — демо-токен не
>    несёт ни `role`, ни `org_id`, поэтому все фильтры дают ноль строк, — но это дыра, и её надо
>    закрыть.
> 2. **Как только вы переключите сервисы в `Production`, `INTERNAL_SERVICE_SECRET` становится
>    обязательным.** В `Development` пустой секрет означает «пропускать», в `Production` —
>    `403 Forbidden` на всех `internal/*` маршрутах. Без него сломается фан-аут заданий (learning
>    спрашивает у identity состав аудитории) и внутренняя оценка в ai.
>
> Делать эти два изменения **вместе**: поставить `ASPNETCORE_ENVIRONMENT=Production` и в тот же
> момент задать `INTERNAL_SERVICE_SECRET` (≥32 символа) в `.env`.

## Шаг 7 — ai-service (**строго раньше learning-service**)

Это **единственное жёсткое межсервисное ограничение всей фазы**, и к нему два блока пришли независимо:

- `dialog.evaluated` получил поля `modeKey` и `qualityScore`, и публикует их ai-service. Поднимете
  learning первым — `AssignmentThresholdConsumer` начнёт получать диалоги без `modeKey` и **молча их
  отбрасывать**. Ничего не упадёт, но диалоги за это окно никогда не пойдут в зачёт заданий.
- learning-service больше **не держит ключей провайдеров вообще**: диалоговое упражнение и синтез речи
  ходят в ai по HTTP (`POST /ai/chat`, `/ai/chat/stream`, `/ai/tts`). Нет ai — не работает упражнение
  `ai_dialogue`.

Обратная стрелка (ai спрашивает learning про контекст задания) **fail-open**: клиент ловит любое
исключение и возвращает `null`, разговор идёт без контекста задания. Поэтому цикл в зависимостях есть,
а тупика нет.

```bash
$DC up -d ai
$DC logs -f ai
```

Применятся `AddOrganizationId`, `RefreshTenantPoliciesForPlatformStaff`, `AddDialogModeOverrides`,
`AddOrganizationProfileReplica`, `AddOrganizationQuotas`.

**Бэкфилла в Postgres у ai нет и не нужно:** все существующие пакеты и режимы — глобальный контент,
`NULL` для них уже правильное значение. Заполнить его означало бы отдать общую библиотеку практики в
частную копию одного заказчика.

Дальше — Mongo и индексы:

## Шаг 12 — включение RLS (**отдельное событие, не в том же окне**)

Это переезд рантайма на роль `sellevate_app` (`NOSUPERUSER`, `NOBYPASSRLS`, не владелец таблиц).

```bash
# 1) один раз на кластер + один раз на каждую БД с RLS-таблицами
$DC exec -T postgres psql -U "$POSTGRES_USER" -d postgres \
  -f - < docs/TENANCY/sql/create_sellevate_app_role.sql
# затем блок GRANT'ов из того же файла — по одному разу на identity, learning, ai,
# company, gamification, social, organization
```

Три вещи, которые надо знать **до** того, как это делать:

1. **Семь фоновых задач замолчат без ошибки.** Это строки `Needs BYPASSRLS = Yes` в
   [`BACKGROUND_JOBS.md`](BACKGROUND_JOBS.md) — те же семь мест, где стоит `IgnoreQueryFilters()`.
   Им нужна отдельная роль с `BYPASSRLS` или явное решение, что они переезжают позже.
2. **Отдельной строки подключения для миграций в коде нет.** Каждый сервис применяет миграции на
   старте (`Database.Migrate()` / `MigrateAndBackfillAsync`) через тот же
   `ConnectionStrings__Postgres`, что использует рантайм, и переключателя «не мигрировать» не
   существует. Значит, простая замена строки подключения на `sellevate_app` сломает **следующий
   деплой с новой миграцией**: у роли нет прав на DDL. Варианта два — либо разнести строки
   подключения (правка кода, ~полдня), либо каждый деплой с миграцией делать двухфазным
   (поднять под владельцем → перезапустить под `sellevate_app`). Это надо решить **до** переезда,
   а не после.
3. Прогнать интеграционные тесты изоляции — единственное, что проверяет RLS **как RLS**:
   ```bash
   for p in src/backend/*/*.Tests/*.csproj; do
     dotnet test "$p" --filter "TestCategory=Integration"
   done
   ```
   Без поднятого локального Postgres они уходят в `Skipped` за секунды, а не висят.

## Ловушки, на которых это ломается чаще всего

1. **Роль миграций без `BYPASSRLS`** → миграции «успешны» и не делают ничего. Шаг 2.
2. **`ORGANIZATION_ID` разъехался между скриптами** → данные в разных организациях-призраках. Во всех
   пяти скриптах должен быть один и тот же `00000000-0000-4000-8000-000000000001`.
3. **learning поднят раньше ai** → диалоги за это окно молча не идут в зачёт заданий.
4. **Забыт `--backfill` после миграции learning** → пользователи видят пустой прогресс.
5. **`MONGO_URI` не переопределён** → скрипт стучится в порт 27018 (локальный dev), а не 27017 (прод).
6. **Переключили в `Production`, не задав `INTERNAL_SERVICE_SECRET`** → `403` на всех внутренних
   маршрутах, ломается фан-аут заданий.
7. **Не прогнаны `--indexes`** → второй заказчик не заводится из-за глобально-уникальных слагов.

## Чего в этой раскатке нет, и это надо знать заранее

- **Ни один вызов LLM за этапы D/E/F не выполнялся.** Формат ответа модели проверен только на
  заглушках. Первый живой прогон шести ИИ-функций этапа F — ваш, и первое, что там может сломаться,
  это **парсинг ответа**, а не логика.
- **Новый HTTP-шов learning → ai ни разу не проходил живьём.** Смотреть три вещи, все про сеть:
  `POST /ai/chat/stream` должен доезжать по частям (NDJSON; буферизующий прокси между сервисами →
  субтитры появятся разом в конце реплики — функционально работает, ощущается сломанным);
  `POST /ai/tts` отдаёт WAV, который должен играть браузер; таймаут крутить надо
  `AiService:ChatTimeoutSeconds` (90 с), а не таймаут `HttpClient` по умолчанию.
- **Таймауты ai-service против конвейера контента** — главное подозрение финального ревью: возможно,
  генерация (40.27) и переписывание тона (40.32) не завершаются для урока реального размера, а каждый
  провал оплачивается трижды и учитывается нулём. Воспроизвести это стоит первым делом, как только
  появится ключ провайдера.
- **Цифры квот выбраны агентом, а не измерены.** Прожить месяц и посмотреть `GET /admin/ai-usage`,
  прежде чем обещать что-то в договоре. И заполнить `AiQuotas:PricePerMillionTokens` реальным прайсом
  шлюза — сейчас он намеренно пуст.
- **Рейт-лимита на `POST /auth/login/start` нет.** Перебором адреса не вытащить (ответ одинаков для
  известного и неизвестного), но каждый вызов — два запроса в identity-db, а лимитов на анонимные
  маршруты в гейтвее нет вообще. Настраивается на гейтвее/реверс-прокси.
