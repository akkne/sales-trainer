# Скилы, темы, уроки и упражнения — справочник по контенту

> Этот документ описывает **модель контента** SalesTrainer и то, как наполнять её
> данными. Если вы пишете контент или импортируете его через seeder/admin API —
> читайте этот файл. Подробные JSON-схемы каждого типа упражнения — в
> [NEW_EXERCISE_TYPES.md](NEW_EXERCISE_TYPES.md).

## Иерархия контента

Контент образует дерево из **четырёх** уровней (а не двух):

```
Skill (скил)
└── Topic (тема)
    └── Lesson (урок)
        └── Exercise (упражнение)
```

> ⚠️ Важно: уроки принадлежат **темам**, а не скилам напрямую.
> `Lesson.TopicId → Topic`, `Topic.SkillId → Skill`. Эндпоинт
> `GET /skills/{slug}/lessons` под капотом находит скил, берёт его темы и собирает
> их уроки.

## Часть 1 — Скил (Skill)

Скил — это верхнеуровневый раздел обучения (например, «Холодные звонки»).

Сущность: `src/backend/api/Features/SkillTree/Models/Skill.cs`

### Поля скила

| Поле | Тип | Описание |
|------|-----|----------|
| `Id` | GUID | Первичный ключ |
| `IconicName` | строка | Уникальный slug-идентификатор. Используется как «адрес» скила в URL: `GET /skills/{IconicName}/lessons`. Должен быть уникальным и не меняться после создания |
| `Title` | строка | Название, которое видит пользователь. Например: `"Холодные звонки"` |
| `Description` | строка \| null | Необязательное описание |
| `OrderInTree` | число | Порядок отображения скила в дереве. Меньшее — выше |
| `Stage` | строка | `key` этапа воронки для группировки на `/tree`. По умолчанию `"general"`. Этапы хранятся в БД (`SkillStages`) и редактируются в админке (`/admin/skill-stages`); встроенные ключи: `preparation`, `discovery`, `engagement`, `closing`, `retention`. |

> Полей `slug`, `iconName`, `sortOrder`, `prerequisiteSkillId`,
> `applicableSalesTypes` в коде **нет** — это устаревшие имена из старой версии
> документа. Идентификатор называется `IconicName`, порядок — `OrderInTree`.

## Часть 3 — Урок (Lesson)

Урок — контейнер для упражнений.

Сущность: `src/backend/learning-service/Learning/Features/Lessons/Models/Lesson.cs`

### Поля урока

| Поле | Тип | Описание |
|------|-----|----------|
| `Id` | GUID | Первичный ключ |
| `OrganizationId` | GUID \| null | Фаза 40.10. `null` = глобальная библиотека, общая для всех заказчиков; заполнено = собственная копия одной организации |
| `TopicId` | GUID | К какой теме относится урок |
| `Title` | строка | Название урока |
| `OrderInTopic` | число | Порядок урока внутри темы |
| `Slug` | строка (160) | Фаза 40.15. Устойчивый идентификатор урока внутри организации, `UNIQUE (OrganizationId, Slug)` |
| `ParentLessonId` | GUID \| null | Фаза 40.15. Заполнен, если этот урок — override глобального. Никто его пока не пишет: создание override'ов это 40.18 |
| `IsArchived` | bool | Фаза 40.15. Урок на пенсии, но не удалён — на него ссылаются опубликованные версии и исторический прогресс |

> Поля `xpReward` у урока **нет** — баллы прогресса начисляются логикой прогресса, а не из поля.

> **Про `Slug`.** Заголовки уроков — русская проза, и агент их **не транслитерирует**: таблица
> транслитерации это долгоживущая догадка о том, как «Работа с возражениями» должно читаться
> латиницей, о которой никто не просил. Урок без явно заданного слага получает машинный
> `lesson-<32 hex его собственного id>` — уникальный по построению. Задать читаемый — это
> переименование через `PUT admin/lessons/{id}`, и оно безопасно ровно потому, что по слагу пока
> ничего не маршрутизируется.

## Часть 3.5 — Версия урока (LessonVersion), фаза 40.15

Урок правят, и правки надо переживать: если админ исправит правильный ответ, а исторические попытки
ссылаются на изменяемое содержимое, то **точность по навыку — то самое число, которое РОП покупает
как меру готовности команды — задним числом меняется**. Заметив это один раз, заказчик перестаёт
верить дашборду, и будет прав.

Отсюда версии. Полный проект модели — [TENANCY/CONTENT_MODEL.md](TENANCY/CONTENT_MODEL.md) §2;
здесь — то, что уже работает.

Сущность: `src/backend/learning-service/Learning/Features/Lessons/Models/LessonVersion.cs`

**Единица версионирования — урок целиком вместе с упорядоченным набором упражнений.** Не строка
`Lessons` (у неё нет тела — только заголовок) и не каждое упражнение по отдельности: версионировать
упражнения порознь значит превращать любой исторический вопрос в раскопки по N строкам версий. Урок
весит килобайты — копируется целиком.

| Поле | Тип | Описание |
|------|-----|----------|
| `Id` | GUID | Первичный ключ |
| `OrganizationId` | GUID \| null | Денормализованная копия организации урока. Денормализована потому, что RLS-политика умеет сравнивать только колонки той строки, которую фильтрует |
| `LessonId` | GUID | Какой урок |
| `VersionNumber` | число | Монотонно, с 1, уникально в пределах урока |
| `Content` | jsonb | Снимок: заголовок + упорядоченные упражнения с их содержимым |
| `ContentHash` | строка (64) | SHA-256 в hex от **канонического** `Content` |
| `Status` | строка | `draft` \| `published` \| `archived` |
| `BaseVersionId` | GUID \| null | От какой версии родительского урока форкнут override (нужно 40.18) |
| `IsBreaking` | bool | Правка косметическая (`false`) или смысловая (`true`) |
| `CreatedBy` / `CreatedAt` / `PublishedAt` | | Аудит |

### Три правила, которые важнее полей

**1. `draft` мутабелен, публикация замораживает строку навсегда.** Не «по договорённости», а
триггером в базе (`LessonVersions_reject_frozen_change`): после выхода из `draft` нельзя изменить ни
содержимое, ни хеш, ни номер версии, ни урок, ни организацию, ни `IsBreaking`, ни время публикации;
`published` умеет уйти только в `archived` и никогда обратно в `draft`. Снимок, который можно
поправить задним числом, — это не снимок.

**2. Черновик у урока максимум один.** Частичный уникальный индекс
`UNIQUE ("LessonId") WHERE "Status" = 'draft'`. Проверка в C# здесь не работает: два админа,
нажавшие «редактировать» одновременно, — это ровно та гонка, которую проверка-перед-вставкой
проигрывает, а два черновика это две ветки урока без стратегии слияния (автомерж прозы и критериев
оценки даёт правдоподобную бессмыслицу, которая потом оценивает продавца).

**3. Публикация без изменений не плодит версию.** Перед публикацией снимок пересобирается и хешируется;
если хеш совпал с последней опубликованной версией — не публикуется ничего, ответ приходит с
`createdNewVersion: false`. Хеш считается по **каноническому** JSON (ключи объектов отсортированы),
иначе перестановка ключей при пересохранении выглядела бы как правка содержимого и версия росла бы
на каждом сохранении — то есть `content_hash` не делал бы того единственного, ради чего он есть.

### Откуда берётся содержимое версии

Строки `Exercises` остаются **рабочим представлением**, которое правит админка. Черновик — это
зеркало рабочих строк: его снимок пересобирается из живых `Lesson` + `Exercises` при каждом
обращении, поэтому разъехаться с тем, что админ видит на экране, он не может. Отдельно строка
черновика хранит то, чего у рабочих строк нет: кто начал править, когда, от какой базовой версии
форкнуто и сам факт «у этого урока есть неопубликованные изменения» (это читает очередь ревью
в 40.18).

### Форма снимка

```json
{
  "exercises": [
    { "content": {}, "customAiPrompt": null, "exerciseId": "...", "orderInLesson": 1, "type": "choose_option" }
  ],
  "schemaVersion": 1,
  "title": "..."
}
```

`exerciseId` лежит внутри снимка и, значит, внутри хеша — это та идентичность, которая нужна 40.16,
чтобы сказать, *какое упражнение внутри какой версии* решал человек. Принятая за это цена: удалить
упражнение и создать заново с тем же содержимым даёт новый хеш и новую версию. Это честный ответ —
идентичность действительно изменилась.

### Что с этим сделал блок 40.16

Попытка (`UserExerciseAttempt`) и прогресс по уроку (`UserLessonProgress`) теперь несут
`LessonVersionId` — тот самый снимок, по которому ответ оценивался. Второй колонки под
«идентичность упражнения внутри версии» не понадобилось: это и есть `exerciseId` из снимка выше,
поэтому `ExerciseId` остался на месте и поменял смысл, а не форму.

Практический смысл для того, кто правит контент: **правка становится видимой для истории в момент
публикации, а не в момент сохранения**. Опубликовали смысловую правку (`isBreaking: true`) —
исторические цифры остались при старой версии, а новая начинает свой отрезок графика. Опубликовали
косметическую (`isBreaking: false`) — отрезок продолжается, ступеньки на графике не появляется.
Сохранили упражнение и **не** опубликовали — продавцы уже видят новый текст, а попытки продолжают
записываться на предыдущий снимок; так задумано (`docs/DECISIONS.md`), но помнить об этом надо.

Точность по версиям читается через `GET /admin/lessons/{lessonId}/accuracy`
([API_CONTRACTS.md](API_CONTRACTS.md)); правила её интерпретации — в
[ANALYTICS_SERVICE.md](ANALYTICS_SERVICE.md).

## Часть 3.7 — Версия программы (ProgramVersion), фаза 40.17

Скилы, темы и уроки выше — это **библиотека**. Программа — это отдельная вещь: упорядоченный список
ссылок на то, что именно и в каком порядке проходит конкретная организация. Она не содержит ни
одного байта контента.

```
ProgramVersion      id, organizationId, versionNo, status
ProgramItem         programVersionId, skillId, lessonId, lessonVersionId, orderIndex
ProgramEnrollment   userId, programVersionId
```

**Три правила, которые важнее полей.**

1. **`ProgramItem` пинит `lessonVersionId`, а не `lessonId`.** Программа ссылается на замороженный
   снимок урока. Урок могут переиздать десять раз — человек, зачисленный на эту версию программы,
   продолжает видеть тот снимок, на который его зачислили, пока сам явно не перейдёт.
2. **Структура — только ссылки.** Переставить скилы местами значит создать новую `ProgramVersion` с
   другими `orderIndex`. Ни один урок, ни одно упражнение и ни одна `LessonVersion` при этом не
   пишутся. Именно это отличает «настроить программу под заказчика» от «форкнуть библиотеку»
   ([CONTENT_MODEL.md](TENANCY/CONTENT_MODEL.md) §1).
3. **Опубликованная версия программы заморожена — вместе со структурой.** Заморозку держат два
   триггера в базе, и важнее тот, что на `ProgramItems`: правка задним числом переставила бы
   программу под человеком, который на 8-м уроке из 21, а это ровно то, ради чего блок и написан.

**Зачисление устроено несимметрично, и это главное.** Админ организации ставит новичков на самую
свежую опубликованную версию (`POST /admin/program/enrollments`) и **никогда** не двигает того, у
кого зачисление уже есть — повторный вызов возвращает его как есть. Переход на новую версию делает
сам обучающийся (`POST /program/switch`), явно, назвав ту версию, диффом которой ему показали, что
изменится. Маршрута, которым админ переносит чужое зачисление, не существует.

**Что показывает дифф.** Четыре корзины: уроки добавились, уроки убрались, урок остался, но
перепинен на другой снимок, и урок остался на том же снимке, но переехал (другой порядок или другой
скил). Последняя корзина — это и есть всё содержимое перестановки скилов, и она же доказательство,
что перестановка не тронула контент. Флаг `isBreaking` у перепиненного урока считается **не** по
целевой версии, а по всем опубликованным версиям этого урока между двумя пинами: программа может
перескочить сразу несколько версий, и смена правильного ответа в версии 4 иначе спряталась бы за
косметической версией 5.

**Пока программы нет — ничего не меняется.** Организация, которая не опубликовала ни одной версии
программы, работает ровно как раньше: люди читают живое дерево, зачисления ни у кого нет, доступ к
урокам зачислением не закрыт. Миграция не создаёт «версию 1» и никого не зачисляет — в отличие от
40.16, где «версию 1» урока создать было можно, потому что тело урока уже существовало. Программа —
это решение, которого ещё никто не принял (`docs/DECISIONS.md`).

## Часть 3.8 — Override контента (copy-on-write), фаза 40.18

Организация хочет поправить формулировку в уроке, добавить свои возражения в технику, переписать
промпт персоны. Очевидный ход — при онбординге скопировать ей всю библиотеку — **запрещён**: после
пятнадцати заказчиков будет пятнадцать форков, улучшение базового урока не дойдёт ни до кого, а
каждая правка базы превратится в пятнадцать ручных слияний.

Вместо этого — **copy-on-write**: копия одной строки создаётся ровно в тот момент, когда админ нажал
«редактировать», и никогда раньше.

```
Lesson             ParentLessonId  -> глобальный урок, форком которого является эта строка
LessonVersion      BaseVersionId   -> конкретный замороженный снимок базы (40.15)
Technique          ParentTechniqueId + BaseContentHash + IsArchived
ReferenceMaterial  ParentMaterialId  + BaseContentHash + IsArchived
DialogMode         ParentModeId      + BaseContentHash            (ai-service, другая БД)
```

**Резолв на чтении.** Фильтр тенантности отдаёт «моё или глобальное», поэтому организация с тремя
override'ами видела бы эти три урока **дважды**. `ContentOverrideResolution` — недостающая половина:
глобальная строка прячется, если у организации есть живой override на неё. Применён только на
пользовательских путях чтения (дерево навыков, списки уроков, разблокировка следующего урока,
техники, справочник). Админские пути намеренно видят обе стороны — экран ревью для того и
существует, — а платформенный персонал не резолвит вообще, иначе правка одного заказчика скрыла бы
глобальный урок от сотрудника Sellevate.

У техники это не косметика, а корректность: override носит слаг базы (так URL справочника не
ломается при кастомизации), и без резолва поиск по слагу находил две строки.

**Очередь stale считается на чтении, нигде не хранится.** У урока сравниваются id версий: база
опубликовала что-то новее того снимка, из которого форкнули, — значит stale. У техники, справочника
и промпта версий нет, поэтому точка форка — это `BaseContentHash`, отпечаток базы на момент форка;
база «сдвинулась», когда её текущий отпечаток отличается. Отпечаток намеренно не включает `Id`,
`OrganizationId` и `UpdatedAt`: база, пересохранённая без изменений, не изменилась, а очередь,
которая кричит на каждое пересохранение, учит читателя прокликивать её не глядя.

**Автомержа нет и не будет — и дифф на сервере тоже не считается.** Контент — это проза и критерии
оценки; трёхстороннее слияние даёт правдоподобную бессмыслицу, которая потом оценивает живого
продавца. API отдаёт три документа целиком; текстовый дифф — это первая половина мержа, и как только
он появится, «ну примени хотя бы неконфликтующие куски» станет продуктовым разговором.

**Три действия ревью.**

| Действие | Что делает | Почему так |
|---|---|---|
| Принять базу | override **архивируется** (`IsArchived`, в ai-service — `IsActive = false`) | Удалять нельзя: попытки, прогресс и сессии диалогов ссылаются на строку без внешнего ключа |
| Оставить override | точка форка перепривязывается к текущей базе, контент не трогается | Ровно для этого 40.15 оставил `BaseVersionId` изменяемым на замороженной строке |
| Править | обычные админские маршруты правки | Публикация новой версии override'а перепривязывает базу сама, поэтому правка снимает запись из очереди без отдельного действия |

**Кто что может писать.** С 40.18 четыре контентных контроллера — уроки, упражнения, техники,
справочник — открыты админу организации (`RequireOrgAdmin`) плюс проверка владельца строки в коде:
строка с организацией принадлежит ей, строка без организации — общая библиотека и требует
платформенных прав. Создание контента с нуля осталось платформенным. Проверка **не** может быть
политикой RLS: контентная политика в `WITH CHECK` разрешает `OrganizationId IS NULL`, потому что
читать общую библиотеку заказчик обязан, — а как правило записи это означало бы «любая организация
может писать в общую библиотеку». В БД зафиксирована та половина, которую БД выразить может: три
CHECK-ограничения «у override всегда есть владелец».

**Экрана ревью нет.** Фронт в блоке не трогался — админка РОПа это 40.20, и она ждёт дизайн от
владельца. См. `docs/DONT_FORGET.md`.

Проект модели целиком — [TENANCY/CONTENT_MODEL.md](TENANCY/CONTENT_MODEL.md) §1 и §2.6, решения и

## Оценивание

### Шкала

Все типы возвращают `score` в диапазоне **0–100**.

- **Детерминированные** (`choose_option`, `fill_blank`, `reorder`) — бинарно: 100 при верном ответе, 0 при неверном.
- **С частичным зачётом** (`match_pairs`, `categorize`) — `score = доля верных × 100`; `isCorrect = true` только если верны **все** элементы.
- **AI-оцениваемые** (`spot_mistake`, `rewrite`, `ai_dialogue`, `evaluate_call`, `free_text`) — модель возвращает `rating` 1–10, итог `score = rating × 10`.

### AI-модель и формат ответа

- Модель: `gpt-4.1-nano` (production) / `gpt-4.1-mini` (development).
  Ключ конфигурации: `OpenAI:OpenQuestionModel`.
- AI возвращает JSON: `{ "passed": bool, "rating": 1-10, "feedback": "текст" }`.
- Правило прохождения для AI-типов: `isCorrect = passed || rating >= 8`
  (порог `8` зашит в коде, см. `AiEvaluationStrategyBase`).

> ⚠️ Конфиг `ExerciseEvaluation:PassingScoreThreshold` (по умолчанию `7`)
> присутствует в `appsettings.json`, но в текущей логике оценивания **не
> используется** — AI-порог зашит как `rating >= 8`. Не полагайтесь на этот ключ
> при настройке контента.

### Промпты для AI-типов

Итоговый системный промпт собирается из двух уровней:

1. **Глобальный промпт типа** — таблица `ExerciseTypePrompts` (поле `SystemPrompt`),
   управляется через admin API (см. ниже).
2. **Промпт упражнения** — поле `ai_prompt` **внутри `SerializedContent` JSON**
   (каноническое место; колонка `CustomAiPrompt` — не используется оценщиком).

Они объединяются как: `[глобальный]` + `Дополнительные критерии:` + `[упражнения]`
+ инструкция о формате ответа.

**Валидация контента:** При создании/обновлении упражнения через admin API (`POST /admin/lessons/{id}/exercises`, `PUT /admin/exercises/{id}`) и при импорте (`POST /admin/lessons/{id}/exercises/import`) поле `content` валидируется серверной стороной per-type. Одиночные операции возвращают 400 с объединёнными ошибками; импорт валидирует per-item, пропускает плохие элементы и возвращает ошибки в response.

## Прогресс и статусы

### Статусы скила (вычисляются на лету)

Статус считается из количества пройденных уроков скила
(`SkillTreeService`), а **не** из цепочки prerequisite:

```csharp
status = completedLessons == 0          ? "available"
       : completedLessons >= totalLessons ? "completed"
       : "in_progress";
```

| Статус | Значение |
|--------|----------|
| `available` | Доступен (ещё нет пройденных уроков) |
| `in_progress` | Есть хотя бы один пройденный урок |
| `completed` | Все уроки пройдены |

> ⚠️ Механики **блокировки скилов prerequisite-цепочкой нет**. Поля
> `UserSkillProgress.Status` / `UserLessonProgress.Status` со значением по
> умолчанию `"locked"` существуют, но в расчёте дерева скилов сейчас не
> участвуют — все скилы стартуют как `available`. Если потребуется реальная
> блокировка, это нужно реализовать.

### Что происходит при верном ответе

1. Записывается попытка `UserExerciseAttempt` (UserId, ExerciseId, ответ, IsCorrect, Score, AI-фидбек, AttemptedAt).
2. Обновляется прогресс урока, начисляются баллы прогресса, проверяются вехи компетенций.
3. Пересчитывается статус скила по формуле выше.

> ⚠️ **Очереди повтора упражнений нет.** Старая версия документа описывала
> систему «ошибся → упражнение в конец урока, до 3 попыток» — в коде такой
> механики **не существует**. Каждый сабмит просто создаёт новую запись
> `UserExerciseAttempt`; ограничения на число попыток нет, пользователь может
> отправлять ответ сколько угодно раз.

#### Bundle import — всё дерево одним файлом

`POST admin/seeder/bundle` (лимит 20 МБ) принимает **весь контент-граф разом**:
скил → темы → уроки → упражнения. Это самый удобный путь «посадить админа и
залить контент». В UI — вкладка **Bundle Import** (`/admin/import`) с кнопкой
Download Template.

Формат файла — объект `{ "skills": [...] }` (или просто массив скилов):

```json
{
  "skills": [
    {
      "iconicName": "cold-calling",
      "title": "Холодные звонки",
      "description": "…",
      "orderInTree": 1,
      "stage": "preparation",
      "topics": [
        {
          "iconicName": "cold-calling-basics",
          "title": "Основы",
          "orderInSkill": 1,
          "lessons": [
            {
              "title": "Открытие звонка",
              "orderInTopic": 1,
              "exercises": [
                { "type": "choose_option", "orderInLesson": 1, "content": { /* по схеме типа */ } },
                { "type": "free_text", "orderInLesson": 2, "content": { /* … */ }, "customAiPrompt": null }
              ]
            }
          ]
        }
      ]
    }
  ]
}
```

Upsert-ключи те же, что у пошаговых сидеров (скилы/темы по `iconicName`, уроки по
`(TopicId, Title)`, упражнения по `(LessonId, OrderInLesson)`) — **повторный
импорт того же файла безопасен**. Контент каждого упражнения валидируется по типу
до записи; невалидные упражнения пропускаются и попадают в `errors` с указанием
пути (`Lesson '…', exercise N (type): …`), остальное дерево создаётся.

Ответ — `BundleImportResultDto`: счётчики `*Created`/`*Updated` по каждому уровню
плюс `errors[]`.

## Пакетная адаптация тона и ИИ-ревью упражнений (Phase 40.32)

Две операции над **уже существующими** упражнениями, обе — над целым этапом (`Skill.Stage`) сразу,
обе — через одну и ту же машину. Полное описание: [CONTENT_PIPELINE.md §6a](CONTENT_PIPELINE.md),
маршруты — [API_CONTRACTS.md](API_CONTRACTS.md).

| Режим | Вопрос | Что приезжает на упражнение | Можно применить |
|---|---|---|---|
| `tone_rewrite` | «Перепиши под наш продукт и тон» | переписанное тело + фраза модели о том, что изменено | **да**, поштучно, человеком |
| `quality_review` | «Что не так с этим упражнением» | список кодов из закрытого словаря | **нет** — это диагноз, а не патч |

**Ничего не применяется само.** Фоновый воркер пишет только предложения; единственный код, который
пишет `Exercise`, — обработчик запроса администратора, и он принимает **одно** предложение по его id.
Кнопки «применить всё» нет и не должно быть.

**Приём предложения по упражнению из общей библиотеки сначала форкает урок** (copy-on-write из 40.18)
и пишет тело в копию организации. Новая версия урока при этом **не публикуется** — правка ложится в
черновик, ровно как `PUT /admin/exercises/{id}`, и до учеников доезжает, когда кто-то опубликует
версию.

### Семь кодов ИИ-ревью

Закрытый словарь. Модель возвращает **код и дословную цитату** из упражнения; русская фраза и
серьёзность (`blocking` / `advisory`) живут на сервере, поэтому два прогона над одним упражнением
дают одно и то же замечание, а «сколько у клиента упражнений с этим дефектом» — это запрос, а не
чтение.

| Код | Серьёзность | О чём |
|---|---|---|
| `ambiguous_correct_answer` | blocking | Правильный ответ неоднозначен: ещё один вариант можно защитить |
| `multiple_correct_answers` | blocking | Верных вариантов буквально больше одного |
| `obvious_distractors` | advisory | Неверные варианты слишком очевидны — упражнение ничего не проверяет |
| `answer_given_away` | advisory | Формулировка задания сама подсказывает ответ |
| `unmeasurable_criteria` | blocking | Критерии свободного ответа непроверяемы («ответил хорошо») |
| `missing_explanation` | advisory | Не сказано, почему верный ответ верен |
| `banned_claim_rewarded` | blocking | Верный ответ содержит или поощряет запрещённое обещание организации |

Последний — самый острый и ради него ревью вообще получает профиль организации: упражнение, чей
**правильный** ответ содержит запрещённое обещание, не просто разрешает его, а учит произносить и
ставит за это высокий балл.

**Пустой ответ ревью — ожидаемый и нормальный.** Упражнение без замечаний закрывается как
`unchanged` и до очереди человека не доезжает; то же с переписыванием, которое ничего не изменило.
Ревьюер, который всегда что-нибудь находит, перестаёт быть авторитетом к десятому упражнению.

> **Microservices (Phase 8):** the content described here is now owned and served by the extracted **[learning-service](LEARNING_SERVICE.md)** through the gateway (Postgres `learning` DB). Paths, schemas and behaviour are unchanged. AI-graded exercise types are scored by the learning-service calling the ai-service `POST /ai/evaluate` (the learning-service still owns the `ExerciseTypePrompt` text and passes it in).
