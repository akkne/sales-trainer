### [x] A-1 POST /tracking/events отдаёт 503 при каждой полной загрузке страницы
- **Где:** любой экран приложения (воспроизведено на `/profile`, `/tree`, `/guidebook`, `/dialog`, `/companies`, `/discuss`, `/settings`, `/session/...`, `/reference/...`)
- **Что делал:** открывал страницу по прямому URL (жёсткая загрузка), смотрел сетевой лог вкладки.
- **Что произошло:** `POST https://api.sellevate.site/tracking/events` → **503**. При этом при клиентской навигации (клик по ссылке в сайдбаре, без перезагрузки) тот же запрос с телом `{"event":"page_view","page":"profile"}` возвращает **204**. Сервис аналитики жив: ручной `POST /tracking/events` с невалидным телом отвечает корректной 400-валидацией (`Sellevate.Analytics.Features.Tracking.Models.TrackEventRequestDto`).
- **Ожидалось:** 204 и на первой (жёсткой) загрузке страницы.
- **Слой:** infrastructure (диагностировано — не код; см. ниже)
- **Severity:** minor
- **Резолюция:** diagnosed, mitigated client-side, server action pending. Отклонена гипотеза «токен ещё не готов» — `hasAccessToken()`/`fetchWithAuthToken` читают `accessToken` из `localStorage` синхронно, до любых других эффектов, так что заголовок уже стоит на первом же тике жёсткой загрузки. Отклонён и код: `TrackingController.TrackEvent`/`UsageEventRecorder` — чистый синхронный инкремент Prometheus-счётчика без I/O, физически не может ответить 503; хуже, что он может — 400. Отклонён и гейтвей: в `Gateway/Program.cs` нет ни рейт-лимитера, ни кастомного маппинга ошибок (`GatewayErrorCorsMiddleware` перечисляет только 502/504/404), а у кластера `analytics` в `ReverseProxy:Clusters` нет ни `ActiveHealthCheck`, ни `PassiveHealthCheck` — путь YARP `NoAvailableDestinations → 503` не подключён для этого маршрута. Отклонена и гипотеза «общий сбой Kafka/Redis» — identity-service и learning-service гейтят `/readyz` по тем же Redis+Kafka проверкам, но их `/auth/me`, `/skills`, `/skills/{slug}/lessons` в том же прогоне отвечают 200 на тех же жёстких загрузках, где `/tracking/events` отдаёт 503. Остаётся связность между gateway и подом `analytics-service` (единственная реплика, `/readyz` зависит от Redis и Kafka) либо K8s/сетевой слой перед ним — вне видимости этого репозитория и вне разрешённых в этом прогоне действий (без доступа к серверу). Точный механизм, что менеджеру проверить на живом кластере и почему пул `analytics-service` — не Kafka/Redis в целом — единственный правдоподобный код-видимый кандидат, записаны в `docs/DONT_FORGET.md`. Существующая клиентская митигация (`a83ef12`, 5-секундный таймаут) не тронута и продолжает не блокировать UI.

### [x] A-5 В справочнике техник нет фильтра по навыкам: /techniques/meta отдаёт skills: []
- **Где:** `https://sellevate.site/guidebook` (строка фильтров)
- **Что делал:** открыл `/guidebook`, посмотрел строку чипсов-фильтров и ответ `GET /techniques/meta`.
- **Что произошло:** в строке фильтров есть только чип «Все». `GET /techniques/meta` → 200 `{"skills":[],"totalCount":45,"userCounts":{"mastered":0,"master":0,"unseen":39}}`. При этом `GET /skills` возвращает 13 навыков. Дополнительно: `mastered 0 + master 0 + unseen 39 = 39`, а всего техник 45 (6 техник не попадают ни в одну корзину).
- **Ожидалось:** непустой список навыков для фильтрации и суммы корзин, равные 45.
- **Слой:** backend
- **Severity:** minor
- **Резолюция:** факеты и фильтр по навыку в `TechniqueService` учитывали только `PrimarySkillId`, а техники в реальности размечены через `AdditionalSkills` (тот же союз полей, который `GetTechniqueBySlugAsync` уже использует для `skillIconicNames`) — отсюда пустой список. Теперь оба места (счётчик фактов и `?skill=`-фильтр) объединяют `PrimarySkillId` и `AdditionalSkills`. Несовпадение `mastered+master+unseen ≠ totalCount` — не баг: `mastered`/`master` вложены по дизайну (разные пороги мастерства), а `unseen` считается от «есть хоть какой-то прогресс», так что «увиденные, но не дошедшие до mastered» техники не попадают ни в одну из трёх экспонируемых корзин. Объяснено в docs/API_CONTRACTS.md; см. docs/DECISIONS.md.

- `/verify-email?token=<битый>`: параметр `token` в этом потоке не используется вовсе — подтверждение идёт 6-значным кодом (`POST /auth/verify-email`), ссылок с токеном бэкенд не рассылает (в шаблонах писем таких URL нет). Без ожидающего email страница показывает корректное русское состояние «Подтверди свой email · Начни со входа — код придёт на твой email» и кнопку «Войти». Не дефект.
- `/dialog` открывается, оба блока («Кастомный сценарий» и «Диалоговые модули») наполнены.
- Токен доступа живёт 15 минут и молча продлевается через `POST /auth/refresh` при перезагрузке — просроченный токен на 401 не «выкидывает» из приложения.
